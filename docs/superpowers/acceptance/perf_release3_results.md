### Profiling the flagged prior suspect

`atlas_objects.AtlasService._build()`'s "unresolved work" section builds one `FieldMarkService.build(room_id)` call **per eligible room** rather than a single UNIONed statement (`atlas_objects.py`, module docstring + the loop around line 511). Timed directly against the same seed-scale connection AtlasService itself uses (not through HTTP, so this isolates DB + Python cost from network/uvicorn overhead):

- Eligible rooms for `amo-seed@fixture.example.com`: **41**
- Full `AtlasService._build()` (direct DB call): **181.6 ms**
- The per-room `FieldMarkService.build()` loop alone: **85.4 ms** (47.0% of the total), ~2.1 ms/room

That loop is a substantial share of Atlas's own cost at this membership scale (40 eligible rooms for the heaviest-membership user) — each iteration is a full `field_marks` fetch capped at 500 rows, fenced and re-derived from scratch, for every room the caller belongs to, on every Atlas load. It does not, on its own, explain a target miss if Atlas otherwise meets the target (see the pass-2 table above), but it is the mechanism to revisit first if Atlas's p95 regresses as membership counts grow — a single UNIONed, per-partition-capped statement (the house pattern §1.6 already uses everywhere else in this module) would turn N round trips into one.
