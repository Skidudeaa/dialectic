Start here — the part that touches our build

What transfers to Dialectic, and what doesn't

Dialectic is the harder case: two humans and an LLM co-reasoning as equal participants, event-sourced, over WebSocket, with threads that fork. Everything here is drawn from the review that follows — a verified assessment of a mature single-user agent-memory layer — governed by one caveat: there is no published prior art on multi-party conversational memory. Not thin evidence; none. So this is reasoning by analogy from 1:1 systems, and per-speaker attribution in a three-way setting is unmeasured by any benchmark in this review.

Port

  • Three-lane RRF recall, largely unchanged. We already have pgvector and 1536-d embeddings — this is a query-function port, not an architecture change.
  • Add speaker_id to the entity lane so a three-way conversation gets per-speaker attribution instead of one undifferentiated "user".
  • The nullable-column-plus-optional-filter pattern maps cleanly onto per-speaker vs shared-room memory, shared tier as the null case. Note the inversion: the soft-scoping default that's arguably a bug in a single-user agent is the correct default here, because three-way dialogue needs cross-speaker reads.
  • Both dedup passes. Two humans restating the same point in different words is the common case, and trigram catches near-restatements embeddings smooth over.

Don't port

  • Paging tiers. Measured at 32.4s vs 1.0–1.5s per turn — disqualifying when the model must decide mid-conversation whether to speak.
  • Inline entity extraction. In Dialectic the write path sits on the hot conversational loop, and Mem0's own ablation shows it costs 3.2× search latency for a per-category accuracy loss. Extract asynchronously off the event log, if at all.

Event sourcing does not make validity windows redundant

The log gives time-travel over what was said. Validity windows track when a fact was true. Two different timelines, and collapsing them loses one. Note that memory_history() in the reference implementation is itself a derived projection, not a substitute source of truth.

The right port: make supersession a materialized projection rebuilt from the event log — log authoritative, memory table a fast index over it. That resolves fork genealogy for free. A forked thread inherits the projection as-of the fork point and then diverges, because the projection is a pure function of the ancestor event prefix. No memory copying, no cross-fork contamination, re-derivable at any time.

≈1s

The latency budget for the interjection engine. Flat-retrieval systems land at 1.0–1.5s total per turn and full-context at 1.726s. One indexed RRF query plus generation is the only viable shape — anything with a recursive read path is out.

The cost argument lands here before accuracy even enters: the ~10-turn crossover at 100k context sits squarely in Dialectic's regime, since a two-human dialogue passes ten turns almost immediately.

The rest of this page is the review those recommendations come from — what the system is, whether it holds up, and which widely-repeated arguments about agent memory turned out to be wrong.

Verdict

Convergent, not over-engineered. The honest criticism isn't complexity — it's the absence of measurement.

Three-lane fused retrieval, temporal validity, write-time consolidation and importance weighting are what Zep/Graphiti ships in production and what Mem0 independently converged on in its v3 pipeline (April 2026). Two funded companies arriving at the same shape from different directions is the definition of convergent design, not over-building.

Two details are ahead of where hobby work usually lands: a pg_trgm trigram pass sitting alongside cosine dedup, and entity extraction made non-blocking and disableable — the latter being precisely the hedge Mem0's own ablation says you need. What separates this from what serious teams ship isn't architecture. It's that they have a benchmark number and this doesn't yet. That's one script, not another year of building.

The single highest-leverage finding

The embedding model dominates most of the architecture around it

+6.2pp

MemDelta ran a byte-identical pipeline differing only in embedder — same chunking, same top-k, same vector store, same prompt, same answer model, same judge. all-MiniLM-384d scored 47.2% on LongMemEval-S; OpenAI text-embedding-3-small-1536d scored 53.4%. p = 0.004, paired McNemar. Per-category the gains land exactly where memory systems claim their value: temporal +10.5pp, multi-session +11.3pp.

That delta is as large as the architectural gains whole papers rest on — and the author already has it banked. The schema header confirms text-embedding-3-small, 1536-d.

The uncomfortable half of the same paper: naive top-k RAG on that embedder came within 1.2pp of Mem0 (73.9% vs 72.7%, matched n=88). One component swap flips a headline verdict. So the elaborate machinery in any of these systems — this one included — is unproven relative to embedder choice until someone runs the control arm.

3–0 confirmed  Caveat: single-author unreplicated preprint, and MiniLM-vs-OpenAI is weak-vs-strong rather than two peer modern embedders, so treat +6.2pp as an upper-ish bound.

Repo audit

The code is real, and more conservative than the write-up

Verified directly against schema.sql in the published template: three RRF lanes with k constant int := 60, HNSW m=16 / ef_construction=64, dedup similarity_threshold float DEFAULT 0.95 plus a separate pg_trgm pass for template variations that escape embedding detection, valid_from / valid_until / superseded_by with a memory_history() replay function, and entity extraction via gpt-4o-mini explicitly optional and non-blocking.

Three deviations worth naming yourself, before someone else finds them:

The claimed quality control isn't in the published code

Direct source verification

No LLM judge, no nightly scoring table, no regression gate, no cron pruning job, no thumbs-feedback loop exist in the open-source template. They live only in the private harness and are therefore unverifiable from outside. Since they are the claimed quality-control layer, the public artifact currently has no measurement story at all.

Project isolation is soft, not hard

Direct source verification

project is a nullable column commented "namespace / tenant tag, null = global", and every function takes filter_project text DEFAULT NULL — omit the parameter and you read across all projects. That's namespacing with cross-project retrieval allowed by default, the opposite of "every memory is project-scoped." Supabase RLS appears in the README as available, not as applied in the schema.

Importance weighting is roughly ±20%

Direct source verification

The blend factor is (1.0 + 0.04 * (importance - 5)) across the full 1–10 scale, and recency decay is capped so old-but-relevant memories lose at most 25%, with preferences and corrections exempt entirely. "Corrections outrank passing comments" is delivered mostly through tie-breaking ORDER BY clauses in the FTS and entity lanes, not through the score blend.

The code being more hedged than the prose is the right direction for a discrepancy to run — but the prose should be corrected to match.

Recommendations

Cut, keep, add

Cut

  • Inline entity extraction on every write. The only component with direct published evidence against it — and it's Mem0's own ablation.
  • LoCoMo as a gate. 50 conversations, ~26k tokens, two speakers, fits inside any modern window, with a documented ~6.4% answer-key error rate.
  • Any temptation toward MemGPT / MemoryOS-style paging tiers. Measured at ~30× flat retrieval on user-facing latency.

Keep

  • Three-lane RRF retrieval — this is table stakes, not invention, but it's correct.
  • Both dedup passes. Trigram catches near-template restatements that embeddings smooth over.
  • Supersession and validity windows.
  • text-embedding-3-small.
  • The capped decay — cheap, conservative, doing no harm. Just don't defend it on benchmark grounds; nothing here supports Ebbinghaus-style forgetting curves.

Add

  • An external benchmark harness.
  • Judge calibration against a small human-labelled held-out set.
  • A reranking stage. Zep ships five — RRF, MMR, node-distance, episode-mention frequency, cross-encoder. This system has zero. Clearest gap vs. the reference architecture, but unmeasurable until the harness exists.

Why extraction is the cut

2–1 contested

Mem0's paper, Table 1, per-category LLM-as-judge: single-hop 67.13 ± 0.65 without graph vs 65.71 ± 0.45 with; multi-hop 51.15 ± 0.31 vs 47.19 ± 0.67. Confidence intervals don't overlap on either, so the direction isn't noise. Latency 0.148s → 0.476s p50, memory tokens 1,764 → 3,616. The paper's own reading: "the addition of graph memory in Mem0g does not provide performance gains here, indicating potential inefficiencies or redundancies in structured graph representations."

Two caveats that matter. On the headline aggregate Mem0g actually wins (68.44 vs 66.88). And independent 2026 work finds graph retrieval gives roughly +27 average multi-hop gains when paired with multi-step traversal, with ablations showing one-shot retrieval is what fails. So the evidence is against one-shot entity lookup on conversational memory, not relational structure as such. Gate it or batch it async — the code already supports disabling it, so this is a config change with a measurable outcome.

Sequenced by value per unit of effort

What to actually do, in order

  1. 01

    Run LongMemEval-S with three arms

    Full-context baseline, naive top-k RAG on the identical embedder, and the full system. Highest value by a wide margin — without it every other decision is guesswork, and the naive-RAG arm is the one that reveals whether the last year of work earned its keep.

    Pass condition: beat 53.4% by more than its 49.0–57.8 confidence interval. At or below that, the RRF fusion, entity lane, importance blending and supersession stack is buying nothing over a single cosine query on the same embedder. Beating full-context is a stretch goal, not a pass condition.

  2. 02

    Calibrate the nightly judge before trusting it as a gate

    The comfortable defence — "absolute judge scores drift but relative orderings between systems stay stable" — was refuted 0–3 in verification. What is documented is LoCoMo's judge accepting ~62.8% of deliberately wrong answers. Treat the nightly judge as an uncalibrated instrument until it's scored against a small human-labelled held-out set. That calibration is a prerequisite for it functioning as a regression gate at all.

  3. 03

    Gate or async-batch entity extraction

    Removes hundreds of LLM calls a day and, per the ablation above, plausibly improves single-hop and multi-hop retrieval rather than degrading it. The code already supports disabling it — this is a config change with a measurable outcome.

  4. 04

    Decide project scoping deliberately

    The code defaults to cross-project reads via filter_project DEFAULT NULL, contradicting the stated design. Either make the filter mandatory or drop the hard-isolation framing from the description.

  5. 05

    Run MemoryAgentBench FactConsolidation

    The only harness that tests supersession and selective forgetting — i.e. the validity-window machinery specifically. Best published single-hop is 54.0% (HippoRAG-v2); every system scores at most 7% multi-hop despite all of them implementing invalidation machinery. Any non-trivial result there would be genuinely novel. This is the one place in the whole review where a new result was within reach.

  6. 06

    Add a reranker

    MMR at minimum, cross-encoder if budget allows. Real gap versus the reference architecture — but it stays unmeasurable until 01 exists, which is why it's last rather than first.

The obvious objection

"Why not just stuff a million tokens in?"

Don't claim retrieval wins on accuracy. That argument won't survive scrutiny, and both sides of it are vendors describing themselves. Zep reports beating full-context on LongMemEval (71.2% vs 60.2%). Mem0 reports the opposite on LoCoMo, conceding verbatim that "the full-context approach can provide a slight accuracy edge" (72.90 vs 66.88). A 2026 preprint has long-context GPT-5-mini beating its own memory system by 35pp — a finding that runs directly against its authors' commercial interest, which is the least bias-prone direction evidence can point.

Cost and latency are clean, though. Crossover at roughly ten turns for a 100k context, ~26% cheaper by turn 20 — and the 90% prompt-caching discount was applied exclusively to the long-context arm, biasing the test against memory. Break-even falls as context grows: 30k → 13 turns, 100k → 10, 200k → 9, 500k → 9.

Context also isn't free even ignoring price. Anthropic names "context rot" explicitly; NoLiMa (Adobe Research, ICML 2025) found 11 of 13 models claiming 128K+ context fall below half their short-context baseline by 32K tokens. One 2026 caveat: this has improved markedly for the best models, so say "degrades on nearly all models tested", not "all".

Justify retrieval on cost, latency and context hygiene. Not on an accuracy win.

Evidence ledger

Confirmed findings and how they fared

The three-lane design is convergent with shipped production systems

2–1 contested

Zep combines cosine similarity, Okapi BM25 full-text and breadth-first n-hop graph search, fused with RRF — verified verbatim in the arXiv HTML and still current in Graphiti's July 2026 docs. Mem0 v3 independently converged on the same three signals. Qualifiers: Zep's third lane is n-hop BFS over a temporal knowledge graph, this one is flat entity matching; Mem0 fuses additively rather than by rank, so RRF specifically is less universal than the three-lane pattern it fuses.

arXiv:2501.13956Graphiti docs, Jul 2026mem0ai/mem0#4805

LoCoMo is not a defensible external gate

3–0 confirmed

50 conversations, ~600 dialogues and ~26,000 tokens each, two speakers per conversation, fitting entirely inside any modern context window. A 2026 audit found ~6.4% of the answer key wrong — 99 of 1,540 score-corrupting errors — meaning the ~6-point deltas papers report on it may sit inside its own error floor. LongMemEval exists precisely because of this: LoCoMo "does not effectively test critical memory capabilities such as knowledge updates." Most papers also evaluate on the released 10-conversation subset rather than all 50, which strengthens the critique.

Supersession targets the field's genuinely weakest axis — but having the mechanism isn't evidence it works

2–1 contested

MemoryAgentBench probes four competencies across 22 systems and 5 backbones and states plainly that "current methods fall short of mastering all four." On selective forgetting: "all methods fail on the multi-hop situation (with achieving at most 7% accuracy)." The systems scoring ≤7% already implement invalidation machinery — which is exactly why running the split matters rather than assuming. Note that scheduled decay and pruning is a different mechanism that this benchmark does not measure, so the weekly decay job cannot ride this citation.

Hierarchical paging is disqualified for anything interactive

2–1 contested

Independent third-party evaluation, user-facing latency per turn: full context 1.726s; flat-retrieval systems 1.06–1.46s; MemoryOS 32.372s, of which 31.247s is read. Verbatim: "strict hierarchical paging (e.g., STM-LTM recursion) is impractical for interactive settings." Qualifier: n=1 implementation, undisclosed hardware, and Letta/MemGPT was never actually measured — cite the ~30× relative gap, never 32 seconds as a portable constant.

Unanswered, not answered negatively

Six questions the research could not close

Memory poisoning and injection — zero verified coverage, and the most serious gap.

Roughly 207 memories a day are auto-persisted from text the agent read across ~100 git repos and external sources. A system that writes untrusted text into a store later retrieved as authoritative context is precisely the shape MINJA-class attacks target. Nothing on this survived verification, which means it is unexamined rather than cleared.

Whether 0.95 cosine is a defensible dedup threshold on text-embedding-3-small.

No embedding-similarity distribution study survived, so it's unknown whether 0.95 almost never fires or is quietly merging distinct facts. The pg_trgm second pass is weak circumstantial evidence the author already found cosine alone insufficient. This one is answerable in a single SQL query over the existing 17k rows — pairwise cosine distribution among same-type memories, plus counts of trigram-caught vs cosine-caught merges. That would settle empirically what no published study here could.

IR evidence for RRF's marginal gain and its sensitivity to k=60.

k=60 is the canonical Cormack value used unchanged, but nothing verified here validates it for a three-lane memory workload.

pgvector HNSW vs IVFFlat recall degradation as rows grow, and Supabase small-tier behaviour.

17k rows sits far below where HNSW recall is normally a concern — but the index uses untuned pgvector defaults with no ef_search set, which means it hasn't been tuned as the scale narrative implies.

Whether thumbs up/down feedback measurably improves retrieval.

Nothing survived — and that component is also absent from the published repo.

Prior art on memory for multi-party or group conversation agents, as opposed to 1:1 assistant chat.

Nothing. Which means every recommendation in the Dialectic section at the top is transfer-by-analogy from 1:1 benchmarks, and per-speaker attribution in a three-way setting is unmeasured by any benchmark named in this review.

The actual question

"Am I losing my mind?"

No. Building this was not unreasonable, and it is not the shape of someone losing perspective. The design independently reproduces what two funded companies ship, the single biggest quality lever was pulled correctly by accident or instinct, and two implementation details are more careful than the average production system.

The gap between this and what serious teams ship isn't sophistication. It's that they can point at a number. Everything in the ranked list above exists to get you one.

Method. Six search angles fanned out in parallel; 29 sources fetched and read; 145 falsifiable claims extracted; the top 25 put through three independent skeptics each, prompted to refute, requiring 2 of 3 to kill a claim. 11 confirmed, 14 refuted, 0 unverified. Bias flags. Vendor authorship is pervasive: the two most-cited benchmark sources (Zep, Mem0) are each vendors describing themselves, and they publicly contradict each other — Mem0 recomputed Zep's LoCoMo 84% down to 58.44%; Zep counter-claims 75.14% and alleges harness errors. Where those papers are used here it is deliberately against their own interest. Three load-bearing sources are unreviewed preprints. Mem0's numbers are April 2025 and Zep's January 2025 — both predate mature 1M-token context with prompt caching, so quote them as "what that paper showed at that date", never as standing fact about 2026.
